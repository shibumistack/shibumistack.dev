01

Connect

Run one installer.

Run this from your project root. The shell downloads reviewed TypeScript to a temporary file, Bun runs it with terminal prompts, then the file is removed.

curl -fsSL https://shibumistack.dev/install/ship.sh | sh

The installer validates your Git project, adds owned ship source and package commands, then connects setup. Existing edits to scripts/ship.ts are never overwritten.

Setup suggests the domain, asks once for your normal user@server target or SSH alias, and registers the current branch. It saves server targets in mode-0600 local settings, reuses them for later projects, and installs or upgrades shibumi-server through confirmed SSH when needed.

If no tracked Compose file exists, setup offers to generate a bounded Bun Dockerfile, loopback-only compose.yaml, and secret-safe .dockerignore. Review, commit, and push them, then resume with bun ship:setup. Existing files are never overwritten.

If DNS or webhook delivery is not ready, setup keeps the owned files. Complete the printed action, then resume with bun ship:setup. No reinstall needed.

Cloudflare: For proxied domains, set SSL/TLS encryption mode to Full (strict). Flexible mode sends HTTP to Caddy, causing an HTTPS redirect loop. GitHub reports stopped after 10 redirects, and webhook setup cannot finish.

03

Deploy

Push when ready.

bun ship

Ship requires committed work on the configured branch. It runs project tests and checks, builds the server's Linux image from exact HEAD, and uploads it through SSH. Only then does it push Git and follow deployment status. It never stages or commits files for you.

Existing domains keep their current Caddy upstream until first Shibumi deployment passes health checks and you approve cutover. Use bun ship:logs for latest deployment log or bun ship --rollback to restore previous retained image.

Agents can use bun ship -y for a prompt-free run. -y is short for --yes. Bun forwards it directly, so no -- separator is needed. Safety checks and failures remain active.
